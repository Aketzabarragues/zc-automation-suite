Arquitectura OB1 · single-process · single-tenant

Del clic del ratón al PLC: cómo funciona la arquitectura web

Una sola analogía para entenderlo todo: la app es un S7-1500 con un HMI web. El main.py es el OB1 (cíclico), el tia-loop es el hilo de periferia (único dueño del wrapper .NET), y la SPA es el HMI. Lo demás son FBs, DBs y un bus de eventos.

Equivalencias PLC ↔ App
OB1 (cíclico 100 ms) → main-loop ejecuta engine.run_cycle()
Hilo de periferia .NET → tia-loop (único dueño del wrapper Siemens)
FB (Function Block) → FunctionBase con nStep + tracker
DB (Data Block) → store.js en SPA + AppState backend
HMI (panel táctil) → SPA Vue 3 (ShellSidebar, plcpanelview, etc.)
Bus de eventos → EventBusSync + SSE

1. El árbol de procesos: un solo Python, 3 hilos daemon

Cuando ejecutas python main.py, arranca un único proceso Python (la CPU del PLC). Dentro, tres hilos daemon hacen el trabajo (los OB del OB1, por decirlo así).

Proceso único Python · 3 hilos daemon · TIA Portal y navegador fuera del proceso

2. Flujo end-to-end: el botón ↻ Refrescar

3. State machine del tia-loop

El tia-loop NO ejecuta comandos a pelo. Tiene una state machine (como los modos de operación de un PLC: STOP / RUN / ERROR). Esto evita race conditions con el wrapper .NET (que es single-threaded y no tolera accesos concurrentes).

El state se publica al bus SSE → la SPA lo pinta en TiaConnectionIndicator

4. El bus SSE: cómo el backend empuja al frontend

Sin polling. El backend tiene un EventBusSync interno. Cuando algo cambia (un FB avanza un step, el state del TIA cambia, un log se añade), se publica en el bus. El endpoint /stream de Flask mantiene 1 conexión HTTP abierta por SPA y le empuja los eventos en formato SSE.

FAQ operario

¿Por qué Flask NO toca el wrapper .NET directamente?

El wrapper es single-threaded (los RCW de .NET no toleran accesos concurrentes desde el mismo proceso). Si Flask lo tocara en cada request, y Flask es threaded=True, dos requests podrían reventar el wrapper. El tia-loop es el ÚNICO que lo toca, vía la cola FIFO. Flask solo encola comandos y espera la respuesta.

¿Por qué 3 hilos y no 1 solo asyncio?

El wrapper .NET bloquea el hilo Python mientras hace la llamada COM (sync). Si todo fuera asyncio, una llamada bloqueante tiraría el event loop y ninguna otra request avanzaría. Separar en hilos es la forma pythónica de mezclar I/O bloqueante (TIA) con I/O no-bloqueante (HTTP). Trade-off aceptado: pierdes paralelismo, ganas simplicidad.

¿Por qué un EventBus y no llamadas directas entre hilos?

Sin bus, el main-loop tendría que hacer store.tiaConnection = ... desde su hilo, y Flask leería esa variable desde otro hilo. Eso son race conditions garantizadas. Con bus + SSE: el publicador encola, el suscriptor (hilo de Flask que mantiene el SSE) consume. La SPA actualiza su store desde el SSE, sin tocar variables cross-thread en Python.

¿Por qué no hay autenticación?

Single-tenant (un operario por puesto, red local industrial). El binding a 127.0.0.1:9484 solo expone a la máquina local. Si Aketza quiere exponer la SPA a la red, hay que añadir auth + bind a 0.0.0.0 con firewall — pendiente.

¿Qué pasa si TIA Portal se cierra mientras opero?

El handler que esté ejecutándose lanza COMException. El tia-loop captura la excepción defensivamente, transiciona a error y publica el nuevo state al bus. La SPA lo refleja en el TiaConnectionIndicator (rojo) y resetea el state PLC. El operario ve "TIA no responde" en la ConsolaLogs y sabe qué pasó.

¿Cómo se añade un comando TIA nuevo?

1) Añadir _h_xxx(args, tia_client) en tia_handlers.py. 2) Registrar en register_core_commands. 3) (Opcional) Exponerlo vía un endpoint en routers/ que llame a tia.submit_and_wait('xxx', args). 4) (Opcional) Botón en la SPA que llame al endpoint via api.js.
